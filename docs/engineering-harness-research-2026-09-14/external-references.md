## Focused comparison conclusions

### Fusion patterns

Fusion360 MCP demonstrates a useful parameter/introspection/mutation split: read parameters/bodies/features/sketches first, then mutate through typed tools. Its `update_user_parameter` snapshots all user parameter expressions before mutation and attempts restore on `computeAll()` failure. That is a good **pattern**, but it is not a general rollback solution: it covers user parameters, not arbitrary geometry/features, exported files, or another writer’s concurrent changes.

### FreeCAD projects

`blwfish/freecad-mcp` is richer and more mature for state, diagnostics, fixtures, async jobs, and broad FreeCAD workbench coverage. It also deliberately grants the agent arbitrary FreeCAD Python / filesystem / OS reach, so it must be wrapped with explicit path, operation and approval fences before use in this public safety-gated repo. `CREATeNG/freecad-mcp-bridge` is simpler and attractive for explicit per-session local toggle and page history, but its central operation is still Python execution in a live FreeCAD session; deterministic typed engineering gates are not verified here. No unconditional winner: the former is richer but broader risk; the latter is smaller but less domain-enforced.

### KiCad projects and MVP suitability

KiCad is the strongest MVP candidate because Primary already has KiCad source artifacts, raw `kicad-cli` ERC is documented as working, PCB/DRC are concrete current failure surfaces, and no native CAD install is needed for a later test fixture if the fixture is committed. `blwfish/kicad-mcp` has the broadest tool surface and tests, but Primary already records a current-environment MCP ctx failure for many wrappers. Therefore the MVP should **wrap local deterministic KiCad CLI first**, with MCP optional and health-checked later. `NiRuLabs/kicad-mcp-server` contributes transaction vocabulary and IPC board-state/routing concepts, but requiring a live KiCad IPC token and hidden schematic mode makes it a weaker first proof for this repository.

### Blender/visualization

Raw generated Python (`ahujasid/blender-mcp`) is high-risk for this repo: it enables arbitrary code execution by default and has many network/file operations. Safe mode is useful but not sufficient to turn visualization into engineering validation. Typed deterministic operations and grouped undo (`PoBruno/mcp-blender-agent`) are more compatible with Harness goals, especially refs/nextSteps and graph snapshots/diffs/restores; still, Blender remains a visualization adapter, not a DRC/ERC/mechanical-review authority.

### Unity

Unity MCP is useful as a future XR/Quest/training/digital-twin visualization adapter with editor/test/build tooling. It must not become an engineering validation authority for CAD/EDA/physical evidence.

### AgentCAD / AI-CAD

AgentCAD provides a compact CLI contract: generated CAD code -> versioned STEP/render/metrics/check-spec/diff with JSON stdout. AI-CAD shows a larger filesystem-resumable multi-agent CAD department with deterministic tools and regression-gated promotion. The MVP should adapt their **versioned artifacts, proposal-before-promotion, deterministic measurement, and terminal reflection** ideas while preserving Primary’s existing role/gate model.

### General harnesses

Team Harness is useful for model/worker abstraction, caller context and rate-limit circuit breakers, but it optimizes coordination breadth rather than the Primary’s immediate EDA reliability proof. Agent Harnesses/HARNESS.md and Harness Starter Kit emphasize progressive disclosure, constraints, feedback, memory and evaluation; Primary already has AGENTS/copilot-instructions/skills/workflows, so adding root `HARNESS.md` now would duplicate policy instead of proving reliability. Use the concepts, not the files, in the first MVP.
