# フレームワークの構成

[English](architecture.md) | [日本語](architecture.ja.md) | [ガイド一覧](README.ja.md)

公開正本 [architecture.md](architecture.md) の**日本語読者向け編集版**です。
運用上の規則を元の節番号に沿って説明します。個々の過去レビューや設定変更の長い経緯は
原本に残し、この版では現在値として転載しません。逐語訳・独立した規約ではありません。
共通語彙、役割、スキル、テンプレートに不一致があれば正本を優先し、Issue/ECO で整合させます。

## 1. 目的

単一 AI のもっともらしい回路ではなく、一次資料に基づく判断、担当を分けた独立レビュー、
人間が監査できる意思決定の記録を持つ開発プロセスを作ります。
アーキテクチャ、安全、費用・日程の重要判断は人間の Chief Engineer が最終権限を持ちます。
特定製品専用ではなく、組み込み・ロボティクス・IoT へ再利用できます。

## 2. 主な制御フロー

人間の目標を Hardware Lead が要件へ整理し、部品選定、データシート確認、
回路設計、独立レビュー、検証、Design Complete ゲートへ進めます。
Hardware Reviewer の `CRITICAL` / `HIGH` は Circuit Engineer へ戻し、
修正箇所とその影響範囲を再レビューします。形式的な追認で済ませません。

物理インターフェースが分かれば機械設計・組立証拠を WIP として始められます。
Mechanical Reviewer の重大指摘は Mechanical Lead へ戻し、
電子回路と機械の指摘は同じ `validation/open-issues.md` と同じゲートに集約します。
不足する PCB 寸法は Phase 4a の限定物理準備で供給できますが、
全配線や製造リリースの許可にはなりません。

早期の剛体シミュレーションは固定入力で別の経路を進み、
独立したモデル・結果レビューを受けます。実機や Fusion の承認には接続しません。
APPROVED 組立資料はゲートと該当リビジョンの独立受け入れ後で、
実際の製造・通電などの許可は別に必要です。

## 3. 実装済みの14役

| 役割 | 所有する責務 | 所有しない責務 |
|---|---|---|
| Hardware Lead | 要件受付、委譲、分野間インターフェース完成、証拠引き継ぎ、ゲート、調停 | 詳細回路・機械形状の設計 |
| Component Engineer | 実行可能なら3候補以上の一次資料比較、EOL・供給・開発環境評価、推奨 | 回路構成の最終決定 |
| Circuit Engineer | 承認済み部品と資料に基づく回路・設計理由 | 自分の設計の独立承認 |
| Hardware Reviewer | 回路・PCB の独立した反証的レビューと重大度判定 | 自分で設計を修正すること |
| Mechanical Lead | 機械形状、筐体、WIP 組立・搭載・各工程の証拠、Fusion 成果物 | 電子回路の編集、可視化中の無断再設計、自己承認 |
| Mechanical Reviewer | 形状、組立証拠、製造条件の独立評価。WIP 阻害評価と最終受け入れを区別 | 形状修正、動画・CI による安全認証 |
| Firmware Engineer | 安定した実ピン・インターフェースに沿ったドライバー初期化と設計理由 | 実機向け制御・センサー融合、回路変更、自己承認、flash 許可 |
| Power Engineer | 起用時のシステム電源構成提案、複数レール予算 | 変換回路の詳細実装、特定部品選定、電源構成の自己承認 |
| Manufacturing Engineer | 構造部品の材料、充填、壁数、荷重に対する造形方向など製造条件 | CAD 形状、自己レビュー、物理試験なしの危険エネルギー封じ込め認定 |
| Firmware Reviewer | レジスター・周辺機器、実ピン対応、安全ロジック、前提の独立レビュー | 実装修正、制御設計、実機試験・flash の虚偽主張 |
| PCB Engineer | Design Complete 前の限定 WIP 物理準備、承認済み回路からの配置配線・DRC | WIP を使った全配線・製造解禁、部品・回路方針の再決定、自己承認 |
| Systems Engineer | 分野間インターフェースの判断、トレードオフ、ずれの監査方法 | 機械ファイルの実記入、調整業務の乗っ取り、構成・安全の自己承認 |
| Simulation Engineer | 固定入力、剛体モデル、シミュレーション内制御、実際の数値・図・動画 | 実機 CAD/PCB/BOM、実機制御、FEA/SPICE、自己レビュー |
| Simulation Reviewer | モデル・コード・実結果の独立評価、simulation 内指摘 | モデル修正、共有ハードウェア台帳変更、実機認定 |

全プロファイルへのリンクは[プロジェクト紹介](../README.ja.md#エージェント14役)にあります。
元の4役から実際の必要性に基づいて拡張しました。役割追加の履歴は
[正本 §3](architecture.md#3-agents-14-implemented)と
[architecture-evolution.md](architecture-evolution.md)を参照します。
過去に Firmware Reviewer がいなかった記述は当時の経緯で、現在の独立レビューを省略する理由ではありません。

Hardware・Mechanical・Firmware Reviewer は、明示された主張の確認に加えて、
見落とされた隣接問題を考える Foresight checklist を持ちます。まだ指摘と断定できない懸念は
任意の Foresight notes として分け、新たなレビュー担当を作りません。

ネイティブの custom agent 起動が現在の環境で使えれば利用し、なければ実在する task ツールに
該当プロファイルと必要なスキルを渡します。プロファイルが定義の正本です。
起動・追加作業指示の前に[実行契約](work-execution.ja.md)の予約を成功させます。
frontmatter はスケジューラーではなく、設定は安全な引き継ぎで固定します。

## 4. 並列実行

並列可は並列必須ではありません。独立した入力と別文脈の利点がある仕事だけを分け、
小さなレビューや1本の調査は1担当で行います。共有台帳の公開は常に直列です。

| 作業 | 並列化 |
|---|---|
| 部品候補調査・資料別抽出 | 独立した候補・資料ごとに可 |
| 回路サブブロック | 電源・接地・ピン割り当てを先に直列確定した場合のみ可 |
| レビューチェックの個別走査・別視点の前提確認 | 同じ固定対象への独立走査は可 |
| 要件承認、共有インターフェース、統合 | 不可。単一の整合した判断 |
| PASS/FAIL/CONDITIONAL の最終判定 | 不可。責任を持つ1レビュアーが統合 |
| Design Complete ゲート | 不可。Hardware Lead が判断 |

未記載の段階は Lead の許可なしに並列化しません。
時間・クレジット・同時実行上限は別途合意し、全役起動を推論しません。

## 5. ツールの境界

### 5.1 エージェント呼び出し

`explore` / `research` などは実際の公開ツール一覧で存在を確認して使います。
正本の `rubber-duck` は設計前提を疑う追加視点を指し、Hardware Reviewer の代わりではありません。
環境にそのツールがあると推測して呼び出しません。指摘には担当の provenance を残します。

### 5.2 KiCad

接続・バージョン・個々の操作を実行時に確認します。
プロジェクト構造、接続・ネットリスト、回路パターン、BOM、DRC、図の出力は異なる能力です。
2026-08-31 の接続確認と MCP 不具合の詳細は[英語正本](architecture.md)に残る過去の観測で、
今回の環境の成功・失敗を保証しません。
MCP の不具合と KiCad 本体の不在を混同せず、実在する `kicad-cli` の同等操作が使えれば
その実結果を記録します。ERC は CLI で実行された履歴がありますが、
それは ERC 用 MCP wrapper の存在を意味しません。

### 5.3 機械・組立

モデル作成・読み込み、Animation の操作作成、ネイティブ保存・再読込、動画公開・再生を別々に確認します。
公式 API の説明、SDK のシンボル、公開 MCP ツール、実行成功は別の事実です。
Fusion Animation が指定された複数部品の組立では、実際の native storyboard と再生できる動画が必要です。
未検証の `fusion_*` 名や別レンダラーの画像で代替しません。

正規パラメトリック形状と読める寸法表を維持し、実行不可なら入力と WIP 計画を準備して、
不足する操作と最小の引き継ぎを `BLOCKED` として明記します。
生成・再検査していないレンダーや native animation をあると主張しません。
古い Blender 接続の成功・失敗も現在の能力判定ではありません。

### 5.4 ファームウェア

ARM コンパイラー、PlatformIO、vendor IDE は毎回確認します。
過去にインストール・ビルド成功したことと今の可用性は別です。
使える、または導入可能なツールチェーンがあれば実コンパイルを試し、
なければ未コンパイルと明示します。ソース、linker script、Makefile を持つことは実機試験ではありません。
実接続したツールと実機を使っていなければ「flash 済み」「実機検証済み」と言いません。

### 5.5 剛体シミュレーション

初期エンジンは MuJoCo です。Python・依存関係、オフスクリーン描画、符号化、
native replay を別々に確認します。過去の MuJoCo 3.12.0 / macOS `mjpython` 実績は他の環境の保証ではありません。
Fusion、外部アセット、実機アクセス、GPU fleet は前提ではありません。
合成モデルと不完全な設計 proxy は Design Complete 前に扱えますが、実質量や実アクチュエーターを補作しません。

## 6. 証拠モデル

### 6.1 Source of Truth

重要な数値・設計判断はメーカーのデータシート・文書に結び付けます。
Absolute Maximum Ratings、Recommended Operating Conditions、Typical Characteristics を分けます。
一次資料で確認できない値は `UNKNOWN` とし、似た部品の値を本部品の値として使いません。
保管されたメーカー資料がモデルの事前知識より優先します。

### 6.2 著作権と公開リポジトリ

実データシート PDF 等はコミットしません。`datasheets/` にはメーカー、型番、版、
公開日、公式 URL、取得日を持つメタデータだけを置きます。
設計に必要な最小の事実を `Parameter | Min | Typ | Max | Unit | Source` で抽出し、
原文や図を大量転載しません。法的判断が必要なら所有者・法務に確認します。

### 6.3 Evidence ID

`DS-<CATEGORY>-<NNN>` を使い、カテゴリ内で一意なゼロ埋め連番を割り当てます。
例の `DS-IMU-003` は IMU 関連の証拠を識別する形式です。
すべて `datasheets/evidence-log.md` にメタデータ記録、節・表・ページ、
支持するパラメーター・主張を登録します。指摘、FMEA、ECO、追跡表は引用全文を複製せず ID を参照します。
新しい正規 ID の確保・共有公開は Lead の直列タスクで行います。

## 7. 重大度と FMEA を混同しない

### 7.1 レビューの重大度

| 語 | 意味 |
|---|---|
| `CRITICAL` | 想定される通常動作で故障、破損、危険を生む設計 |
| `HIGH` | 現実的な条件・コーナーで誤動作や信頼性低下の可能性が高い |
| `MEDIUM` | 推奨からの逸脱などでリスクを増すが、明確な機能破綻ではない |
| `LOW` | 機能リスクが小さい体裁・推奨事項・文書の改善 |

指摘には Issue、Rationale、Datasheet Source / Evidence ID、Failure Mechanism、
Affected Component、Recommended Fix、Severity を記録します。
正確なスキーマは共通の hardware-review スキルとレビュー記録を参照します。

### 7.2 FMEA の点数

FMEA は Severity・Occurrence・Detection 各1–10の積で RPN を計算します。
特定 snapshot の欠陥に対する重大度語と、システム全体の将来故障を予測する点数は別の尺度です。
ID で相互参照し、1つの尺度へ統合しません。

### 7.3 FMEA の記録

`validation/fmea.md` に機能・部品、故障モード、局所・システム・ミッションへの影響、
各点数、RPN、対策、推奨処置、担当、状態を記録します。
現場で修理できない用途などでは特に重要で、事後のレビューだけで代替しません。

## 8. Design Complete ゲート

以下の**すべて**が必要です。

1. 未解決 `CRITICAL` がゼロ。`CRITICAL` は accepted-risk にできず、必ず `RESOLVED` にします。
2. 全 `HIGH` が `RESOLVED`、または Chief Engineer の氏名・理由・日付付き `ACCEPTED-RISK`。
3. `requirements/traceability-matrix.md` の全行が `Verified`、または明示的な人間の `Waived`。
4. 対象リビジョンの `validation/fmea.md` をレビュー済み。
5. 対象リビジョンの `validation/change-log.md` に人間が承認した ECO が存在。

組立が対象なら WIP 計画・搭載状態・各工程の証拠をこの前に作り、要件検証と機械レビューに使います。
APPROVED 組立資料は、このゲートと同一リビジョン証拠の独立受け入れ後です。
初期阻害レビューや構造 CI の成功は5条件、Fusion 成果物、実機ゲートを免除しません。
重大指摘の SLA 日数は人間がプロジェクトごとに定め、AI が固定値を発明しません。

## 9. 対立・行き詰まり

各担当が Evidence ID・要件 ID とともに立場を示し、Lead が根拠を比較して不足資料を求めます。
必要なら独立した前提確認を使います。真の分野間トレードオフは Systems Engineer に回し、
なお未解決の技術・安全・事業・日程判断は、両案、根拠、得失、推奨を短くまとめて Chief Engineer へ渡します。
解決と理由を ECO・指摘に記録します。[開発フロー §3](workflow.ja.md#3-対立とエスカレーション)も参照してください。

## 10. 人間の明示的承認が必要な境界

アーキテクチャ、主要部品、データシートが見つからない場合、安全に関わる変更、大きな BOM 変更、
PCB 製造前、機械部品の造形・加工前、実機の初回通電前、初回 firmware flash 前には停止します。
初回通電は `validation/bring-up-procedure.md` を使います。
必須 CI の管理者回避も人間に留保された判断で、§17.1 の制限に従います。
物理基板がないことは flash 済みの主張を許可するものではありません。

## 11. ベンチマークとロードマップ

最初は MCU + IMU + 電源。モータードライバー、リアクションホイール、1軸・3軸姿勢制御、
立つ Cube を目指す段階があります。公開 WIP には3軸 Cube 設計と実行可能な初期シミュレーターがありますが、
製作、実現性、安全の承認ではありません。別製品にも再利用できる構造を保ちます。

## 12. 電源・熱・機械の協調

`hardware/power-budget.md` で各レールの負荷、供給能力、余裕を集約し、サブシステム追加時に更新します。
複雑になったら Lead が Power Engineer を起用し、電源構成提案と複数レール予算を任せます。
単純な単一レールでは Circuit Engineer が維持します。
回転体の振動・発熱が PCB、はんだ、コネクター、IMU の温度依存へ与える影響も回路設計・独立レビューで扱います。

## 13. 将来の統合

SPICE 自動実行、部品データベース、計測器、flash / HIL などは、
実際の接続・操作確認なしに利用可能と仮定しません。
KiCad 内のライブラリ存在だけで非対話的 SPICE 実行経路があるとは言えません。
CAD・Animation は永久に「未実装」扱いするのではなく §5.3 の実行時確認で判定します。
購入ガイドと AI に実接続された機器も別です。新たな能力が確認できたときに正本の該当箇所を更新します。

## 14. 将来の役割

Control Engineer（実機向け制御・推定）、Test Engineer（継続的な実機試験）、
Datasheet Specialist（大量・複雑な抽出）、Safety/Compliance Reviewer（規制・認証）は
必要性と人間の依頼が明確になってから導入します。
表で過去に将来役とされた Power、PCB、Firmware、Firmware Reviewer、Systems、Simulation の役割は
すでに §3 に実装済みです。Manufacturing も実際の製造条件の空白を理由に追加されました。
シミュレーション内制御の存在だけでは実機 Control Engineer を新設しません。

## 15. 評価

[評価方法](evaluation.ja.md)で、同じ要件・部品候補・一次資料に対する単一エージェント方式と比較します。
複数担当に分けたこと自体を品質向上の証拠とはしません。

## 16. ディレクトリ

[プロジェクト紹介の構成表](../README.ja.md#リポジトリ構成)を入口とします。
実行可能な役割・スキルは `.github/`、正規設計値は `requirements/`・`datasheets/`・`bom/`・`hardware/`、
独立評価は各担当の記録先、実行ツールは `tools/` が原本です。
組立は `hardware/mechanical/assembly-evidence/<assembly>/<revision>/manifest.json` と
`<assembly>/current.json`、simulation は `simulation/evidence/<version>/` と
`simulation/reviews/<review-id>/` を使い、スキーマや受け入れ状態を混同しません。
完全なファイル一覧と過去の導入注記は[正本 §16](architecture.md#16-directory-map)に残します。

## 17. 自律作業とセッション間調整

### 17.1 必須ゲートの回避

既定は**必須チェックを回避しない**です。管理者の技術的能力は常時許可ではありません。
公開 PR は開くだけで内容を提示でき、赤いゲートを越えて main に入れると
共有ブランチを凍結する副作用があります。

既存指摘の Severity/Status、`hardware/`・`firmware/`・`bom/` に触れる PR は管理者回避しません。
他の既存指摘による継承失敗も既定は開いたまま待ちます。
自身の新指摘で初めて赤くなる場合も既定は回避不可です。
この最後のケースに限り、公開のみと公開＋凍結の得失を示した後の人間の明示承認が必要です。
認められた回避は理由、承認者、対象チェック、この PR 限定であること、同日フォローを記録します。

古い path-filter 案や branch-protection の観測を現在の設定と解釈しません。
現在の CI の diff-aware 判定を保ち、docs-only の呼称だけで自己免除しません。
設定や enforcement の変更は独立したレビュー対象です。
過去の相反する設定・その訂正の全記録は[英語 §17.1](architecture.md#171-admin-override--required-gate-bypass-policy)に残します。

### 17.2 行動前の検証

安全・範囲・主要判断に関わる人間の発言は、親セッションからの伝言であっても一次記録で確認します。
現在利用可能な session history ツール等で本人の原文を読み、要約の要約を承認にしません。
空の取得結果は確認にも否定にもなりません。確認不能なら重大な行動を止め、試行と不明点を記録します。
確認できた発言は必要な成果物に原文、必要なら訳、方法、session/turn 参照を残し、
具体的な選択と「選ぶ基準」を区別します。

API の時刻差は同じタイムゾーンにそろえます。
branch-protection の詳細 sub-endpoint が以前の設定を HTTP 200 で返す場合があるため、
権威ある API でもどの view が現在値かを確認し、top-level のキーと live PR の独立信号などで裏付けます。

### 17.3 セッション間の不一致・古い状態

伝言と自分の確認結果が違えば、どちらも即断せず Git、PR、一次ファイル、人間の記録を再確認します。
誤りが判明したら同じ公開範囲で訂正し、撤回済みの主張を履歴から消しません。
真の方針対立は双方を示して人間に判断を求め、一方が独断で決めません。

`updated_at` が止まり diff が空でも、作業停止・死亡の証拠ではありません。
plan の調査中と承認待ちは metadata 上で似て見えます。
実際の担当へ直接確認して適切な返答時間を設け、metadata だけで二重依頼・archive をしません。
同時に保存された `RUNNING` もプロセス生存の証拠ではなく、実出力と実行状態を区別します。

### 17.4 根拠

正本は DevOps の branch-protection、行為別の oversight、監査証跡、
マルチエージェントの意思決定管理、実際の事例からの改善を背景にしています。
外部文献の記述はこのプロジェクトの設計 Evidence ID や認証ではありません。
文献・経緯の出典は[正本 §17.4](architecture.md#174-grounding)を参照します。

### 17.5 branch-protection 変更の過去記録

この節の原本は人間による設定変更、復元、再変更を検証した**時系列**であり、
今の保護設定の保証ではありません。単一アカウントの commit author / merged_by だけでは
人間操作とエージェント操作を識別できない点、誰が変更したかと今どう設定されているかが
別の問いである点を保持します。現在値が必要なときだけ現行の権威ある view を確認し、
翻訳作業で設定・レビュー要求・マージ権限を変更しません。
