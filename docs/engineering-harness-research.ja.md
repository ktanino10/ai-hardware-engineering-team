## なぜ最初は KiCad CLI 一つなのか

選んだ案は、native KiCad の ERC/DRC と、証拠からテスト用レビュー準備判断へ
渡す経路を小さく測定するものです。古いレポートをソース変更後にも有効として
使ってしまう、といった Rev5 に関係する失敗を表現できます。ただし fixture の
成功で、実設計の未解決事項が解消したことにはなりません。

Fusion のパラメータ復旧を先に扱う案は別の実行環境・証拠が必要です。
リポジトリ内の模擬ゲートだけでは実ツールの境界を証明できず、
汎用チーム基盤の導入は既存の担当・指示と重複します。そのため、
追加アダプターや工場型の並列エージェント構成は選びませんでした。

CLI-first は外部 KiCad MCP パッケージのインストールや依存追加ではありません。
Primary の「5ツール動作・11ツール失敗」は 2026-08-31 の特定環境の記録であり、
別途比較した MCP リポジトリの固定版にも同じ不具合がある証拠ではありません。
README の機能数・テスト数は、こちらが実行して確認した成熟度ではありません。

## 状態・証拠・権限を混ぜない

操作の進行・成否、検証の判定、証拠の新しさ、ゲートの判断、
復旧結果は別々の項目です。失敗後に `ROLLBACK_OK` になっても、
失敗した操作や検証が `PASS` に変わるわけではありません。
既存 `agent_workflow` の `RUNNING` / `DONE` / `BLOCKED` も別の予約・納品記録です。

明示した直接入力だけをハッシュ照合する最小範囲であり、
未宣言の入力や推移的な依存関係まで自動失効させる仕組みではありません。
任意の別クライアントによる CLI/MCP 呼び出しや、同一 UID の自由な
ファイル操作を防ぐ OS sandbox でもありません。

CODEOWNERS はレビュー担当の宣言で、実際の必須レビュー設定が有効かは
別途確認が必要です。actor/date を書いた JSON は本人確認や人の承認の証明に
なりません。失敗・古い証拠を承認文字列だけで `PASS` に上書きできません。
エージェント定義本文の評価は **NOT_REVIEWED** のままであり、
役割一覧や設定の一致確認を本文レビューと数えません。

## 実測の結論と停止境界

後続の元キャンペーンと中断修正後のキャンペーンは、別リビジョンのまま保存され、
それぞれ予定した120件を実行しました。いずれも強い scripted-reference の
A 群と B 群の信頼性指標は同等で、
**NO_DEMONSTRATED_RELIABILITY_IMPROVEMENT（改善は実証されず）**です。
その結果を、AI や実機が優秀になった証拠に読み替えません。

新たな設計選択、必要ツール不足、所有範囲・後片付けの不確実性、
追加依存や権限の要求があれば、通常の記録を残して担当者・人へ戻します。
実製造、初回通電・flash、実機動作、設計の昇格、本番採用は別の承認です。
この日本語版も、その承認や独立レビューの代わりにはなりません。
